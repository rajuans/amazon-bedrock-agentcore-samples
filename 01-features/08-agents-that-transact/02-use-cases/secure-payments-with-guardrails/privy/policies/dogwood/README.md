# Dogwood temporal policies for payments

AgentCore Policy's **temporal policies** are written in **Dogwood**, an
open-source policy language that builds on Cedar. Dogwood keeps Cedar's
`permit` / `forbid` model and deny-by-default semantics, and adds conditions
over what the agent did earlier in the same policy session. Every valid Cedar
policy is valid Dogwood, so the point-in-time Cedar rules and the temporal rules
live in one policy set: [`payment_guardrails.dw`](payment_guardrails.dw).

| Rule | Kind | What it stops |
|---|---|---|
| `permit_pay_after_quote` | temporal | Paying any address that the trusted `get_merchant_quote` lookup did not return in this session within 15 minutes (prompt-injected or invented recipients) |
| `forbid_over_per_tx_cap` | Cedar | Any single payment above $0.50 |
| `forbid_recipient_not_allowlisted` | Cedar | Any recipient not on the approved list, even if a lookup returned it |
| `forbid_velocity` | temporal | A 6th payment within any 10-minute window (looping agent) |
| `forbid_rolling_spend_cap` | temporal | A payment that brings the last hour's total to $2.00 or more |

`pay_merchant` has **no** unconditional `permit` — its only permit is the
provenance rule, so a payment with no matching lookup is denied by default.

## Files

| File | Purpose |
|---|---|
| `payment_guardrails.dw` | The policy set to deploy (replace the Gateway ARN and allowlist) |
| `schema.cedarschema` | Action schema for the two Gateway tools (`amount` in USDC base units) |
| `agentcore.dwschema` | Local copy of AgentCore's documented temporal event schema (`request` / `response` / `error`, `eventResource`, session pin, 24h cap) — for local testing only |
| `traces/*.log` | One replay trace per scenario (generated by `gen_traces.py`) |
| `test_dogwood_policies.py` | Validates the policy set and checks every verdict |

## Test locally

Build the `dogwood` CLI (Rust toolchain required), then run the tests:

```bash
git clone https://github.com/dogwood-policy/dogwood && cd dogwood
cargo build --release -p amzn-dogwood-cli          # -> target/release/dogwood
cd -  # back to this folder
DOGWOOD=/path/to/dogwood/target/release/dogwood python test_dogwood_policies.py
```

Expected output:

```

PASS  01_happy_path                      pay the looked-up, allowlisted merchant $0.001       ALLOW
PASS  02_injected_recipient              pay an address the lookup never returned             DENY

PASS  04_lookup_expired                  pay 16+ minutes after the lookup                     DENY
```

You can also inspect a single trace, including which rule decided:

```bash
dogwood replay payment_guardrails.dw --policy-schema schema.cedarschema \
  --event-schema agentcore.dwschema --trace traces/07_velocity.log
```

## Deploy to AgentCore Policy

Attach a policy engine to the AgentCore Gateway that fronts your payment tools,
then create each rule with `create-policy`. A temporal policy's statement goes
under `policy` (not `cedar`) in the definition:

```bash
aws bedrock-agentcore-control create-policy \
  --policy-engine-id <POLICY_ENGINE_ID> \
  --name ForbidVelocity \
  --validation-mode FAIL_ON_ANY_FINDINGS \
  --definition '{"policy": {"statement": "<one rule from payment_guardrails.dw>"}}'
```

Before you deploy:

- **Send a session ID.** Every Gateway request must carry
  `x-amzn-bedrock-agentcore-policy-session-id`. With a temporal policy on the
  engine, a request without it fails validation.
- **Start in `LOG_ONLY`,** check the decisions in CloudWatch, then switch to
  `ENFORCE`. Adding or updating a temporal policy ends open policy sessions
  (the next request returns HTTP 409 — start a new session).
- **IAM:** the Gateway role needs `bedrock-agentcore:GetWorkloadAccessToken`.
  The Gateway and its targets must be in the same account and Region.
- **Quotas:** 20 temporal policies per engine, 3 temporal operators per policy,
  24-hour maximum window.

## The session caveat

Temporal history is scoped to a **policy session**, and the caller chooses the
session ID. Scenario `09_new_session_resets` shows the consequence: a new
session starts with an empty history, so the velocity and rolling-cap counts
reset. Treat these rules as limits on behavior **within** a run. The hard
ceiling is the AgentCore **Payment Session** `maxSpendAmount`, which the service
enforces and the agent role cannot raise or reset.

## Local testing vs. AgentCore

`agentcore.dwschema` reproduces the event schema AgentCore documents, but the
local replay is not the service. Two differences to know:

- In AgentCore a **denied** request is recorded as an `error` event, not a
  `request`, so it does not add to later `count` / `sum` totals. The local
  traces stop at the first denial in each window, so both agree on these
  scenarios.
- AgentCore records events from real Gateway calls. Locally, the trace stands
  in for them.
